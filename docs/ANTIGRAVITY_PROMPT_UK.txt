У корені мого локального проєкту MyKep є архів mykep-seo-update-2.6.6.zip. Застосуй SEO-оновлення та запусти застосунок локально. Працюй у два етапи: зараз лише оновлення і перевірка; git commit/push - тільки після мого окремого явного підтвердження після перегляду результату.

1. Знайди справжній корінь Git-репозиторію, перевір поточну гілку, remote і git status. Не друкуй токени, секрети або вміст .env. Не запускай скрипти з архіву автоматично. Розпакуй ZIP у тимчасову папку поза репозиторієм, перевіривши відсутність абсолютних шляхів, ../ і небезпечних симлінків. Усередині - mykep-main/. Це оновлення, створене безпосередньо на базі mykep-main2_6_5.zip.txt (2.6.5-mobile5), а не старий пакет 2.6.4. Старий архів 2.6.4 не використовуй.

2. Прочитай docs/SEO_UPDATE_UK.md, docs/BASELINE_PRESERVATION_UK.md і UPDATE_MANIFEST.json. Архів містить повний знімок, але перенось ЛИШЕ файли з entries маніфесту. Перевір updated_sha256 файлів архіву. Для змінених файлів звір поточний SHA-256 з baseline_sha256; якщо збігається з updated_sha256, пропусти. Якщо поточний файл відрізняється від обох версій або новий файл уже існує з іншим вмістом - зупинись, покажи конфлікти й запитай про злиття. Не відновлюй старий код поверх новішого.

3. Перед змінами зроби резервну копію зачеплених локальних файлів поза репозиторієм. Збережи сторонні незакомічені зміни. Не чіпай .git, .env, локальні середовища, БД, аналітику, секрети й налаштування користувачів. Не видаляй файли, яких немає в ZIP. Не використовуй git reset --hard, git clean або автоматичний stash.

4. У віртуальному середовищі Python 3.11+ встанови requirements-dev.txt. Виконай python -m unittest discover -s tests -v, node --test tests/*.test.cjs, node tests/test_seo_client.cjs та синтаксичні перевірки JS. Повідом окремо про пропущені тести: skipped не вважай успішною перевіркою. Якщо інструментів немає або є помилки - поясни, не приховуй їх і не роби непогодженого широкого рефакторингу.

5. Запусти python -m uvicorn main:app --host 127.0.0.1 --port 8000 (або інший вільний порт, не зупиняючи чужий процес). Для цього процесу задай BOT_MODE=disabled і MYKEP_DB_PATH до окремої тестової SQLite-бази поза репозиторієм. Не редагуй production .env, не запускай Telegram-бота, не підключай публічний тунель. Canonical залиш https://mykep.pp.ua/.

6. Відкрий браузер і перевір головну, розклад, налаштування, онбординг, групи, таймер, навігацію, встановлення/продовження у браузері та /about.html. Перевір /about.html без JavaScript, мобільні ширини, console errors, метадані, JSON-LD, robots.txt, sitemap.xml, llms.txt, llms-full.txt, OG-картинку й редирект /index.html → /. Перевір Service Worker 2.6.6 та офлайн після успішного завантаження. Якщо можливо, перевір оновлення PWA з 2.6.5-mobile5 зі збереженням групи. Відокремлюй від SEO-помилок 503 холодного кешу/недоступність сайту коледжу; не вигадуй розклад. Що неможливо перевірити, явно зазнач.

7. Покажи підсумковий diff, перелік змін, результати тестів, обмеження й локальний URL. Залиш сервер для мого перегляду, вкажи спосіб його зупинки та ЗУПИНИСЬ. На цьому етапі заборонено commit, push, PR, deploy, зміни production та дії в Search Console.

8. Лише коли після перегляду я явно дозволю пуш, ще раз перевір git status, погоджені гілку та remote (якщо неоднозначні - запитай). Додай тільки погоджені файли явними шляхами, без git add .; не включай ZIP, резервні копії, UPDATE_MANIFEST.json, .env, БД, середовища чи сторонні зміни. Перевір staged diff на секрети та зайві зміни. Створи коміт і виконай звичайний push без --force. При конфлікті або відхиленні push зупинись, не роби автоматичний reset/rebase. Врахуй, що push може запускати вже налаштований CI/CD; окремий ручний production-деплой потребує окремого дозволу.

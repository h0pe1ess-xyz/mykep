# Розгортання MyKep 2.6.0

Цей архів — оновлення вихідного коду, а не виконане розгортання. Завантаження на GitHub саме по собі не доводить, що оновився VPS. Antigravity без доступу до VPS має перевірити код, зробити commit/push і повідомити, які серверні кроки залишилися власнику.

## Сумісність і збереження даних

Потрібен Python 3.11 або новіший. Встановіть `requirements.txt` у **нове локальне віртуальне середовище**, а не копіюйте `.venv` з чужого комп’ютера. `tzdata` потрібен, зокрема, для Windows без системної бази часових поясів. Node.js 20+ потрібен лише для тестів JavaScript, не для роботи сайту. Версії залежностей обмежено сумісними діапазонами, але це не повний lockfile; після перевірки у вашому середовищі зафіксуйте фактично перевірені версії за вашою процедурою релізу.

Не видаляйте й не перезаписуйте робочі `.env`, `schedule.db`, `schedule.db-wal`, `schedule.db-shm`. У ZIP цих файлів немає. Нові таблиці `schedule_snapshot` та `bot_reports` й індекси створюються автоматично; історична таблиця `analytics` зберігається. Старі записи `/api/groups` не видаляються, але більше не входять у звіти про перегляди розкладу. Стара таблиця `schedule` не видаляється; новий кеш має інший формат і завантажується з першоджерела.

Перед розгортанням зробіть резервну копію SQLite через штатний SQLite backup API або зупиніть процеси та скопіюйте базу після їх завершення. Не копіюйте лише `.db` під час активного WAL-запису: частина даних може залишатися в WAL. Переносьте шлях до бази поза каталог релізу лише після резервного копіювання та узгодженої зміни `MYKEP_DB_PATH`.

Нові записи статистики й щоденні звіти використовують `Europe/Kyiv`. Часовий пояс старих рядків невідомий: автоматичної небезпечної зміни старих часових міток немає. Через перехід на точніші метрики цифри до й після оновлення можуть відрізнятися.

## Локальний запуск

````bash
python -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows PowerShell замість попередньої команди:
# .\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
# Скопіюйте .env.example у .env, для локальних тестів задайте BOT_MODE=disabled.
python -m unittest discover -s tests -v
node --test tests/frontend.test.cjs
python main.py
````

Відкрийте `http://localhost:8000`. HTTPS обов’язковий для PWA на реальному домені. HTTP за IP комп’ютера з телефону — **не** валідна перевірка встановлення PWA.

При першому запуску без нового збереженого snapshot API може короткочасно повертати 503 з `Retry-After: 30`; сервер уже працює, але розклад ще завантажується. Перевіряйте `/api/health`. Після успішного завантаження наступні перезапуски використовують останній добрий snapshot. Якщо upstream недоступний і snapshot ще ніколи не створювався, це не можна виправити локальним кешуванням: потрібне відновлення доступу до джерела.

## Вебсервер і бот

Рекомендований стартовий варіант для 100–200 одночасних відвідувачів — один асинхронний Uvicorn worker без `--reload`, SQLite на локальному диску, HTTPS reverse proxy. Не множте worker-и «про всяк випадок»: кожен матиме власний upstream-кеш. Спочатку виміряйте навантаження на своєму VPS. Це стартова архітектура, а не гарантія місткості для будь-якого CPU/RAM/мережі.

**Зворотно сумісний режим:** `BOT_MODE=embedded` (типово) і `TELEGRAM_BOT_TOKEN` у `.env`. Запускайте лише один вебпроцес. Бот стартує разом із ним; окремий процес бота не потрібен.

**Рекомендоване розділення для production:** `BOT_MODE=external` у вебпроцесі та один окремий `python bot.py`. Обидва процеси повинні мати однаковий `MYKEP_DB_PATH`, права читання/запису до каталогу SQLite і однакові admin IDs. Шаблони systemd у `deploy/` призначені саме для цього режиму. `BOT_MODE=disabled` вимикає вбудованого бота, але не заважає окремій команді `python bot.py`.

ОС-блокування біля бази перешкоджає дублюванню poller-а на одному хості. Воно не координує різні VPS або різні шляхи до бази. Telegram Conflict означає, що треба знайти й зупинити інший poller, а не нескінченно перезапускати два екземпляри. Якщо встановлено webhook, бот не видалятиме його автоматично: власник має свідомо вибрати polling або власну webhook-архітектуру. Після виправлення конфігураційної помилки перезапустіть бот. Адміністратор повинен спочатку написати йому `/start` і не блокувати його.

За замовчуванням збережено admin IDs із початкового коду. Їх можна перевизначити через `TELEGRAM_ADMIN_IDS`. Токен не додавайте до GitHub, журналів чи повідомлень агента. Не запускайте локального бота з production-токеном, поки той самий токен використовується на VPS.

## Навантаження і спостереження

`/api/health` повертає стан кешу (`updated_at`, `stale`) та стан запису аналітики (`running`, `pending`, `dropped`, `write_error`). ВебAPI не виконує HTTP-запитів до коледжу на кожен перегляд. Один refresh-loop оновлює дані раз на 30 хвилин, а після помилки повторює через 30 секунд. Останній добрий snapshot залишається доступним. Дата початку чотиритижневого навчального циклу — як у вихідному коді: 31.08.2026; для нового навчального року перевірте її в Python і JavaScript.

Черга аналітики обмежена 10 000 подіями, пачка — до 200. Переповнення не блокує сайт: зайві події відкидаються, лічильник і попередження це показують. Graceful shutdown намагається дописати чергу; при аварійному завершенні живлення, `kill -9`, тривалому збої диска або таймауті зупинки останні події можуть загубитися. Це статистика використання, не гарантований журнал фінансових операцій. Стежте за вільним місцем на диску; автоматичне видалення історії не ввімкнено.

Щоденні звіти надсилаються після 22:00 за Києвом, із повтором невдалих доставок раз на хвилину до кінця цього дня. Успішні доставки фіксуються окремо для кожного адміністратора. Звіт — зріз на момент надсилання, а не закритий 24-годинний баланс. За тривалого простою бот не надсилає автоматично звіти за пропущені минулі дні. Як і в більшості систем із зовнішнім API, таймаут після фактичної доставки Telegram може спричинити повтор: гарантії «рівно один раз» між Telegram і SQLite немає.

Для тесту **лише свого staging/локального сервера**, після успішного завантаження розкладу:

````bash
python scripts/load_test.py --url http://127.0.0.1:8000 --group ПІ-24-02 --users 200 --requests-per-user 10 --confirm-owned-server
````

Скрипт створює 200 паралельних клієнтів, по 10 послідовних запитів на клієнта, показує помилки та затримки p50/p95. Ці запити додаються у статистику тестової бази як `loadtest_*`. Використовуйте окрему базу staging; не забруднюйте production-статистику. Не запускайте цей тест проти сайту коледжу чи чужих серверів. Повторіть під HTTPS reverse proxy і зі звичайним використанням телефону, перевірте CPU/RAM/диск, відсутність 5xx і приросту `dropped`.

## Оновлення PWA та відкат

Service worker кешує реальні JS/CSS-файли й використовує нове ім’я кешу. Старі кеші MyKep видаляються після успішного встановлення нового shell; чужі кеші origin не зачіпаються. Для наступного релізу змінюйте версію одночасно в HTML, `style.css` та `sw.js`. Не підміняйте файли поточного релізу на сервері частинами: розгортайте код узгоджено, інакше клієнт може отримати змішані версії.

Якщо хтось бачить стару версію, спершу закрийте всі вікна PWA, відкрийте сайт онлайн і запустіть застосунок знову. Не вимагайте перевстановлення чи очищення всього сховища без потреби: це видалить особисті налаштування та анонімний ID.

Для відкату зупиніть процеси й поверніть попередню версію коду. Наявні таблиці не видалялися. Якщо треба відновити базу, використовуйте резервну копію та врахуйте втрату записів після її створення. Код попереднього PWA теж може бути закешований; контрольований відкат фронтенду вимагає окремої нової версії service worker, а не лише повернення HTML.

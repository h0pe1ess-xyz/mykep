# MyKep 2.9.0

## Що змінено

- Парсер відділяє цикл 1–4 від дати початку. Перевірка виконується за датою конкретного заняття. Невідомі умови, неправильні номери пар, порожні предмети та пошкоджені записи не замінюють останній коректний snapshot. Діагностика показує причину відмови й кількість записів до та після оновлення; зменшення не блокується довільним порогом.
- Прибираються лише повністю однакові записи джерела. Спільні ключі джерела залишають окремі назви груп для клієнта. Заняття з однаковим інтервалом об’єднуються тільки для індикатора поточної/наступної пари, а в розкладі відображаються окремо.
- Dashboard працює зі сьогоднішньою датою Europe/Kyiv. Автоматичний перегляд переходить на наступний тиждень після фактичного завершення суботи або від початку суботи без занять. У неділю відкривається наступний тиждень; пункт «Цей тиждень» дозволяє повернутися до календарного тижня. Ручні 1–4 тижні не отримують вигаданих дат. PNG використовує календар саме показаних даних.
- Офлайн-кеш містить чотири тижні з умовами початку. Збережено до 12 наборів групи й тривалостей, поточна основна група захищена від витіснення. Зміна групи не очищує інші групи. Кеш v2 мігрує тільки власний ключ; UID, onboarding, група й налаштування не скидаються. Неповний старий кеш не видається за повний цикл.
- Джерело має власний час успішної перевірки; це не час звернення телефона. Для незмінених даних API підтримує ETag/304, а заголовки 304 передають новий час перевірки та stale. Стандартні тривалості залишилися 80/60 хвилин.
- Діалоги налаштувань мають спільні закриття, фокус і inert-фон. Особливі вступні й інсталяційні екрани збережені. «Продовжити у браузері» стало помітнішим, сценарій підтвердження збережено.
- «Про дані» має трикутник, який повертається при відкритті. У встановленому iOS PWA оболонка закріплена через fixed/inset:0 з автоматичною висотою, навбар закріплений до viewport. Прибрано помилкове обмеження через clientHeight, яке залишало порожню смугу знизу. Відступ саме під кнопками обмежений 10–16px: завищений inset із простором відсутньої панелі браузера не піднімає їх угору. Список резервує таку саму висоту навбару. Менша visualViewport від клавіатури не задає висоту оболонки. Ураховано fullscreen та standalone.
- За уточненнями користувача повністю видалено нову панель груп/підгруп, кнопку «Сьогодні» та окреме desktop-прев’ю. Заміни на приховане меню немає. Усі явно позначені підгрупи показуються, спільні заняття зберігаються. Можливість вибору підгруп і обраних груп через відхилену панель не поставляється. Навбар зберігає оранжевий колір без світіння. Службові рядки перенесено в кінець прокручуваного списку. Зміна дня не показує технічну плашку перевірки й не повторює рендер після 304. Дати під днями стали світлішими; фокус перемикача більше не обрізається рамкою, а автоматичний вибір називається «Цей тиждень» / «Наступний». Перемикач має назви «1-й тиждень»…«4-й тиждень».
- Старі рядки аналітики збережено з event_kind=legacy_request. Нові view/interaction означають відкриття та дії, refresh означає технічні перевірки й виключений із переглядів. Є денні агрегати, деталі та контроль розміру БД. Унікальні користувачі спеціальності/курсу рахуються через множину UID, а не суму за групами. Позначка (11) не підміняє рік вступу.
- Довідник викладачів оновлюється фоновим сервісом із перевіркою й останньою коректною копією; клієнт має локальний і вбудований fallback. Неоднозначні нормалізовані ініціали не розгортаються у вгадане ім’я.
- VERSION є джерелом версії сервера, клієнта, support report і PWA-кешу. Заморожені ресурси перевіряються SHA-256 перед активацією worker. HTML перевіряється маркером збірки, бо Cloudflare може додавати свій beacon. Неповний реліз не витісняє робочий worker.

## Збереження даних

Робоча локальна БД і .env початкового checkout не використовувалися для міграції або тестів. Тести створюють окрему тимчасову SQLite-БД із синтетичними записами. Перед ALTER на існуючій цільовій БД міграція автоматично створює backup у сусідньому каталозі backups, перевіряє integrity_check і відновлення у тимчасовій копії. Якщо перевірка не пройшла, запуск зупиняється до зміни схеми.

Детальна аналітика не видаляється автоматично. Старі поля й значення не перезаписуються. Доповнюються таблиці агрегатів та вимірів розміру. Повернення старого коду не потребує зворотної деструктивної міграції.

## Перевірки

Виконуються:

```powershell
python -m pip install -r requirements.lock
npm ci --ignore-scripts
python scripts/release.py --check
python -m unittest discover -s tests -p 'test_*.py' -v
npm test
npm run test:browser
```

Браузерні перевірки використовують локальний сервер і синтетичне API. Chromium та desktop WebKit перевіряють офлайн-цикл, зміну групи через налаштування, всі варіанти підгруп, діалоги з фокусом та inert, зменшений viewport під клавіатуру, прокрутку списку груп, декоративний перемикач, свайпи та Back, ширини 320–1440, PNG, зміну доби й тижня. Реальний Chrome worker перевіряється на оновлення, видалення старого кешу, офлайн-перезавантаження, edge-зміну HTML і відмову від неповного shell.

PNG рендериться реально, але системне поширення підмінене тестовою функцією. Це не перевірка меню Share на iPhone. Окремий браузерний тест відтворив зазор 34px на попередньому коді при clientHeight=810 та viewport=844. Після виправлення перевіряється точний збіг нижнього краю оболонки й навбару з viewport, усі вкладки, занижені/завищені виміри, клавіатура, поворот і повернення. Padding safe areas підставлений у тесті, оскільки desktop WebKit не відтворює системні відступи iPhone. Viewport, touch events, desktop WebKit та CPU-throttling не є перевіркою на фізичному старому Android або iPhone. Обидва повідомлені випадки iPhone потребують перевірки нового релізу на телефонах. CI початкового коміту 04d1cc1 пройшов; результат наступних випусків слід перевіряти окремо.

Мікровимірювання dashboard при 6× CPU-throttling: 50 підборів щільності, три повтори до/після, однаковий DOM, базовий boot.js із cf85856. Читання стилів скоротилися з 1350 до 750, геометричні читання залишилися 600, щільність залишилася 2. Час кадрів коливався; це не доказ відсутності лагів на телефоні. Глобальні жести вже зберігали стилі контейнерів на touchstart, а PNG уже генерувався лише при натисканні. Необов’язкові модулі не відкладено без доказу виграшу або ціною ризику user activation.

## Розгортання

1. Не копіювати локальну або тестову БД на сервер. Зберегти чинні .env, DB_PATH, БД, WAL та сховище резервних копій. Цей код не змінює production-конфігурацію.
2. Перед запуском міграції зробити окрему перевірену копію саме серверної БД: `python backup_database.py <чинна-БД> <новий-файл-копії>`. Команда не відновлює дані поверх робочої БД. Зберігати копії з таким самим захистом доступу, як БД, поза публічним каталогом.
3. Підготувати окремий каталог релізу з `dev`, окреме venv і `requirements.lock`. Для наступних змін ресурсів збільшити VERSION, згенерувати `python scripts/release.py` та виконати всі перевірки. Не перевикористовувати номер кешу для іншого набору ресурсів.
4. Зупинити старий процес для зміни схеми, зберегти стабільний шлях БД та атомарно перемкнути код релізу. Запустити штатний web service. Жоден крок тут не виконано на production.
5. Перевірити health, доступ до розкладу, час джерела, authenticated admin refresh, статистику, установлене PWA й офлайн на реальних пристроях. Не додавати студентам примусове оновлення розкладу. Не послаблювати наявні Origin/CSRF/allowlist/ліміти адмінки.

## Відкат

1. Зупинити новий процес і повернути попередній каталог коду/venv. Залишити чинну БД: додані колонки та таблиці сумісні зі старим кодом і не видаляють історію.
2. Для вже встановлених PWA відкотити клієнт окремим релізом із новим VERSION. Повернення старого номера може залишити попередній worker активним. У старому клієнті схема кешу v3 може вимагати повторного онлайн-завантаження; UID, група, onboarding та налаштування залишаються незалежними ключами.
3. Не замінювати БД старим backup без окремого рішення: це втратить записи після копії. За проблем із БД спочатку створити нову WAL-safe копію поточного стану й перевірити відновлення ізольовано.

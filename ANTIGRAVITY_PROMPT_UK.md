# Промпт для Antigravity

Я прикріпив ZIP з оновленим MyKep. Репозиторій: https://github.com/h0pe1ess-xyz/mykep.

Твоє завдання — розпакувати архів, акуратно інтегрувати оновлення в локальний репозиторій, перевірити й завантажити зміни на GitHub. Доступу до VPS у тебе немає: не намагайся підключатися до VPS, змінювати його конфігурацію чи стверджувати, що сайт уже розгорнуто. Працюй локально та з GitHub у межах наявних дозволів.

Спочатку прочитай `CHANGELOG_UK.md`, `docs/QA_UK.md`, `docs/DEPLOYMENT_UK.md` і `DELIVERY_MANIFEST.json` з архіву. SHA-256 у manifest стосується файлів отриманого ZIP до твоїх змін. Сам manifest не включає свій власний хеш.

Розпакуй ZIP в окрему тимчасову папку. Знайди локальний клон потрібного репозиторію або клонуй його, якщо клону немає. Перевір remote, поточну гілку та `git status`. Не перезаписуй мої незакомічені зміни, `.git`, `.env`, робочу `schedule.db` чи її WAL/SHM-файли. Якщо мої незбережені правки перетинаються з оновленням або виникне конфлікт — зупинись і уточни, не відкидай правки й не роби прихований reset/stash.

Отримай актуальний стан remote. ZIP зроблено на основі переданого раніше архіву, а не перевіреного сьогодні HEAD GitHub, тому порівняй версії: інтегруй оновлення зі збереженням новіших незалежних змін. Не застосовуй сліпе видалення файлів, яких немає в ZIP. Не клади весь проєкт зайвим вкладеним каталогом: `main.py`, `static/` та решта файлів мають бути у корені репозиторію. Не коміть зовнішній ZIP.

Збережи дизайн: темна палітра, помаранчеві акценти, таймер-дуга, картки, автори й нижня навігація. Не роби редизайн і не переписуй застосунок на інший фреймворк. Тут потрібно допрацювання адаптації та надійності, а не новий вигляд.

Створи локальне віртуальне середовище з Python 3.11+ і встанови `requirements-dev.txt`. Для тестів задай `BOT_MODE=disabled` та окрему тестову базу: не використовуй production-базу і не запускай локальний poller із production-токеном Telegram. Реальний токен ніде не виводь.

Виконай:

````bash
python -m compileall -q main.py analytics.py bot.py config.py database.py process_lock.py schedule_service.py tests scripts
python -m unittest discover -s tests -v
node --test tests/frontend.test.cjs
python scripts/benchmark_core.py
````

Окремо перевір синтаксис кожного файлу `static/js/*.js` та `static/sw.js` через `node --check`. У переданому результаті виконані 13 Python-тестів і 20 JavaScript-тестів, але 6 HTTP/FastAPI та 4 bot unit-тести були пропущені через недоступні залежності. У твоєму повному середовищі ці 10 тестів мають виконатися, а не залишитися skipped. Якщо тести виявлять помилки — виправ їх точково без редизайну й повтори перевірки. Якщо залежності/інструменти недоступні, не видавай пропуск за успіх: повідом блокер.

Запусти сайт локально. За наявності браузерних інструментів перевір viewport-и 320×568, 360×640, 375×812 (iPhone 13 mini), 390×844, 430×932 та landscape. Перевір прокручування, довгі назви, клавіатуру, онбординг зі списком і пошуком груп, помилку API груп, формальне попередження 80/60 хвилин, PWA-підказки, додаткове підтвердження браузерного режиму, Telegram-підказку, офлайн-кеш і оновлення service worker. Емуляція viewport не є перевіркою фізичного iPhone: чітко розрізняй це у звіті. Не заявляй, що Telegram завжди розпізнається за UA — у деяких версіях це неможливо, для них є загальна інструкція.

Можеш запустити `scripts/load_test.py` тільки проти свого локального/staging MyKep, коли він уже завантажив валідний розклад, з окремою базою та явним `--confirm-owned-server`. Не запускай навантаження проти сайту коледжу або чужих серверів. Не роби висновок про VPS за одним синтетичним бенчмарком.

Перед commit перевір diff, `git diff --check` і список staged-файлів. У Git не повинні потрапити `.env`, реальні токени, `.venv`, `node_modules`, SQLite-бази/WAL/SHM, дампи статистики, логи або кеші Python. Якщо `.venv`, `schedule.db` чи `stats.txt` уже відстежуються репозиторієм, прибери їх **лише з індексу Git** за допомогою `git rm --cached` (для каталогу — `-r`), зберігши локальні дані. Не переписуй історію Git і не видаляй локальну базу.

Якщо все перевірено, створи окрему гілку на кшталт `update/mobile-pwa-stability-2.6.0`, зроби зрозумілий commit і push цієї гілки в `origin`. Якщо така гілка вже існує — вибери нову назву без перезапису чужої роботи. За доступності GitHub-інструментів створи pull request у фактичну default-гілку репозиторію з описом змін та перевірок. Не роби force push і не зливай PR самовільно; якщо я окремо дам явну вказівку оновити main напряму, дій за нею лише після успішних перевірок. Якщо push недоступний через авторизацію — збережи локальний commit і повідом, що треба від мене; не вигадуй успішний push.

Наприкінці українською повідом: що інтегровано, які тести реально виконано, які пропущено/не пройшли, чи перевіряв ти реальний браузер, назву гілки, commit hash, посилання на pushed-гілку/PR лише якщо вони справді створені. Окремо вкажи кроки для власника VPS з `docs/DEPLOYMENT_UK.md`: резервна копія, залежності, один poller, режим embedded/external, перезапуск, HTTPS і перевірка health. Чітко напиши: «Зміни завантажено на GitHub; розгортання на VPS не виконувалося», якщо це відповідає фактичному результату.
